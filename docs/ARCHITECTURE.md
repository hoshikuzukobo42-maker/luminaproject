# 構成と情報の境界

公開文書作成日：2026年9月10日。2026年9月9日までの本体実装を基に、現在重点的に整備している視覚・移動・自律の経路を説明する。過去の実験系を含む全モジュールが同時に稼働しているという意味ではない。

## 基本構成

Luminaは、Godotのアバター・環境と、Python側の要求処理、視覚認識、移動制御、自律監督を接続する。直近の画像推論で検証したモデルはローカルのQwen3.5-4Bで、llama.cppを通じて利用する。

移植可能な移動経路では、認識モデルに渡す情報と、安全に移動するための環境情報を分ける。

```text
眼カメラのRGB画像
  → 対象を指定しないQwen画像推論
  → 検出一覧の検証
  → 人間の指示との照合・対象選択
  → 深度とカメラ情報による距離・位置への対応付け
  → 匿名の障害物地図による経路計画
  → 環境アダプターを通じた移動
  → 新しい観測・停止・安全条件を用いた到着確認
```

この流れは実装上の責務を示す。全ての入力・環境で成功することや、最新の部屋で一連の受入が完了していることを表さない。

## 主な実装単位

以下は本体での主なモジュール名である。公開版は選別したソースであり、本体の設定・データ・素材・依存物まで含むとは限らない。

| モジュール | 責務 |
|---|---|
| `lumina_next/app.py` | サービスの接続と要求の入口 |

| `lumina_next/visual_navigation.py` | 観察・移動ジョブ、受付制御、経路実行、再検証、到着判定 |
| `lumina_next/portable_navigation_contract_v1.py` | 環境非依存の入出力契約と検証 |
| `lumina_next/portable_navigation_core_v1.py` | 深度・地図を利用する共通の移動処理 |
| `lumina_next/godot_portable_navigation_adapter_v1.py` | Godot側の観測・移動機能を共通契約へ変換 |

## 物体を何から理解するか

対象一覧を作る最初の画像推論は、眼カメラの画像を入力とする。人間が指定した移動先の名前、Godotのノード名、対象の正解座標を画像モデルへ渡して検出させる経路ではない。その後に、検証済みの一覧と指示文を照合する。

対応する既知名詞と文法の指示では、照合の一部を決定的なコードで処理し、文章推論2回を省く。これは画像認識そのものを物体名辞書に置き換える方法ではない。一方で、意味の照合や安全検証には辞書・規則を使っているため、「全ての理解がQwenだけで行われる」「事前知識や規則が一切ない」とも説明しない。未知語には追加の推論と照合があり、任意物体の認識を保証しない。

移動に必要な距離、地図、衝突情報は画像とは別の入力である。Godot用アダプターはエンジンのセンサーや移動APIを利用する。したがって「システム全体がRGB画像だけで動く」「環境プログラムと一切接続しない」という構成ではない。画像認識への正解情報の混入を避ける境界と、移動のための環境アダプターを区別している。

## 環境アダプター

共通契約は次の6操作を持つ。

| 操作 | 意味 |
|---|---|
| `capture` | RGB・深度・カメラ姿勢等の観測取得 |
| `build_map` | 移動用の占有地図取得 |
| `ground` | 画像上の対象と実距離・位置の対応付け |
| `navigate` | 所有するコマンドとして移動を要求 |
| `stop` | 対象コマンドの停止と確認 |
| `feedback` | 移動中・到着・停止・失敗等の状態取得 |

境界では共通の座標系、時刻、要求・コマンドの識別子、観測の形式を検証する。深度の不明部分を自由空間と扱わず、地図の障害物情報と意味的な物体名を分ける。

物理面の`surface_id`は、セッション内で単一の衝突形状または不可分な連結部品を識別し、姿勢・形状の変化時に更新する契約である。永続的な物体名や「これはソファ」という答えではない。`role`も障害物・歩行面等の物理的役割である。この性質を環境側が保証できない場合、識別子による同一性の証拠は利用できない。

Godot以外に移す場合は、この6操作を実際のセンサー・地図・移動制御へ接続し、単位、座標、時刻、停止確認、識別子の更新条件を検証する必要がある。契約があるだけでUnity、Unreal、現実のロボットに接続済みになるわけではない。RGBだけによる自律的な地図生成や、実世界での運用をこの文書は保証しない。

旧来の環境依存経路も本体には残る。この文書が説明する移植可能経路の性質を、全ての旧経路へ無条件に当てはめない。

## 到着と安全性

到着高速化は、証拠が十分な場合に追加の重い再認識を省けるかを評価する。証拠不足なら従来の再確認へ戻し、矛盾がある場合は停止する。単に距離が近い、コマンドを送った、移動の受付が成功した、というだけで到着にしない。

`LUMINA_ARRIVAL_POSE_EPOCH_FAST_PATH`は既定無効で、2026年9月9日の反映後も運転上は無効のままとした。安全性や短縮効果を、新しい部屋で測定済みとはしていない。

## 自律行動と人間の要求

自律の空間行動は、人間の要求と同じ視覚・移動サービスへ接続する。直近の画像由来候補を使い、実行時には新しい画像で再検証する。モデルが内部ノード名や生座標を指定して直接移動する経路は受け付けない。移植可能な移動モードが無効なら、自律の空間行動も受け付けない。

人間の視覚ジョブ、受付ロック、停止未確認などを計画前・実行前に検査する。移動・対象観察の開始と終端結果を分け、後続周期で結果を一度だけ回収する。ただし、全種類の実行中動作の中断や、音声・身振り等の実完了確認はまだ共通化しきれていない。

`LUMINA_NEXT_AUTONOMY_ENABLED`も既定無効である。対象を指定しない自発的な周囲観察は未接続として扱い、架空の観察成功は記録しない。この構成は完全自律の達成宣言ではない。
